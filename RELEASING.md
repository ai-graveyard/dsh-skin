# Releasing

The repository and each skin package use separate version fields. The root package stays private; publish only individual skin packages. Git pushes, local tarballs, npm/GitHub releases and site deployment are separate actions.

## Release checklist

1. Update the changed skin's version in both `package.json` and `skin.json`, its README installation examples, and `CHANGELOG.md`. Keep root README examples and collection versions in sync. Increment the version whenever runtime contents change: reusing a tarball path and version can leave stale content in the desktop package-manager cache.
2. Run `pnpm run build` and `pnpm run check`. Commit the regenerated `client.js` alongside its CSS, tokens and build source.
3. Inspect every package and generate release assets:

   ```bash
   pnpm run pack:skins
   pnpm run release:assets
   ```

   Files are written to `dist/releases/`. `SHA256SUMS` and `release-manifest.json` describe the packages generated by this run. Older versioned tarballs are retained because installed profiles can still reference them during upgrades; do not publish every file in a reused output directory indiscriminately. CI uploads `dist/releases/` as `skin-release-assets` from the Node.js 22 validation job.

4. Open the desktop client once, quit it completely, and install a generated tarball with the client's own `dsh` command:

   ```bash
   dsh plugin --profile desktop add ./dist/releases/dsh-skin-<skin-id>-<version>.tgz
   dsh --profile desktop --dump-config
   ```

   On macOS, the bundled CLI is `/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh`. Use the desktop application's Manage dsh command menu to configure the command. Use this same desktop CLI for installation, verification and removal.

5. For a full collection acceptance pass, install all repository skins and compare the installed files before visual checks:

   ```bash
   node scripts/check-installed.mjs <path-to-dsh-home>/profiles/desktop
   ```

   This command requires all skins in the target profile and compares their package metadata, runtime, CSS, tokens, icons and locales. It does not activate skins or prove native visual acceptance. Keep previous tarballs until profiles referencing them have upgraded.

6. Restart the desktop client and enable one skin at a time. Check the composer and keyboard focus, rich conversations, settings and dropdowns, appearance modes, narrow layouts, plugin metadata, reactivation and cleanup. Record the exact client version/build, skin versions, completed states and untested scope in [DESKTOP-QA.md](./DESKTOP-QA.md). Restore the original plugin configuration after testing. Offline previews and automated checks alone do not justify an `Available` status.
7. Confirm npm names, repository/homepage/bugs URLs, and packaged icons/locales. Verify checksums from the release directory with `shasum -a 256 -c SHA256SUMS` (or `sha256sum -c SHA256SUMS` on Linux).
8. Create the Git tag, GitHub release and npm release as separately authorized publishing actions. Use the manifest to select current assets, and update the changelog when those releases actually happen.

## Site deployment

The repository has no automatic npm or GitHub release publication workflow. Pushes to `main` do trigger CI; after both validation jobs pass, the workflow deploys the catalogue through SSH and Docker Compose, then checks the public homepage. A push or a local build alone does not confirm CI success or deployment. Report the pushed commit, CI result and deployment evidence separately.
